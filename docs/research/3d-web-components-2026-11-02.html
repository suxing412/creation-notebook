可探索 3D 网页的组成与评审方法

检索日期：2026-11-02。

版本说明：依据保留正文恢复的系统化方法版；这是文本恢复，不声称与遗失文件字节或哈希一致。

本文讨论以整页三维空间为主体验的网页，不是普通文章里的模型查看器。它是本项目的设计与评审框架，不是行业强制标准。判断重点是：用户能否进入空间、辨认目标、进行有意义的观察或操作、得到内容、恢复或退出，而不是模型与特效数量。

系统如何构成

目标统领；内容、空间、行为共同构成体验核心；表达使其可感知；运行支撑使其可用。 这是系统构成关系，不是六步制作流程，也不是把已有元素重新排一遍。

目标：为谁服务，要理解或完成什么
                ↓ 约束与评价
        ┌──────────────────┐
        │ 内容 ↔ 空间 ↔ 行为 │
        │   ↖─────────↗    │
        └──────────────────┘
                ↕
表达：模型形态、画面、文字、声音与界面
                ↕
运行支撑：资源、程序、加载、设备与恢复机制

可用性、性能、无障碍和验证贯穿整个系统

内容回答“有什么值得理解”；空间回答“对象在哪里、彼此有什么关系”；行为回答“用户如何观察和操作、系统如何变化”。三者相互约束。例如要看清插接方向，既要有正确的连接内容，也要让对象摆放和视角可达，还要允许适当观察或受限移动。表达不只是美化：状态颜色、文字、音效负责让规则与结果可理解。运行支撑也不是最后补上的底座：设备能力会反过来限制场景规模与交互方案。

各部分的输入与产出

下表中的输入是作出决定所需的信息，不表示必须等上一部分全部结束才开始。

部分主要输入需要产出的决定
目标用户需要、项目诉求、使用条件服务谁，完成或理解什么，为什么采用三维，如何判定成功
内容目标、知识、作品或数据内容清单、主次与关系，必须发现或理解的信息
空间内容关系、观察与操作需求对象和区域布局、尺度、路径、视线、目的地及连接关系
行为用户任务、内容、空间条件观察与移动方式、操作规则、状态变化、反馈条件、恢复与退出
表达内容重点、空间结构、行为状态形态、构图、光材质、文字、界面、声音与动效的表达方案
运行支撑体验方案、设备与资源预算资产管线、程序结构、渲染、加载、降级、兼容和验证方案

真正连接各部分的是体验链

内容落到空间对象与位置
  → 用户观察并输入
  → 满足触发条件，系统状态改变
  → 画面、文字或声音反馈
  → 用户从当前或新的视角观察结果
  → 理解内容，继续选择或行动

不是所有体验都必须改变对象：纯观察也可以通过视点与遮挡变化揭示信息。关键是说明“这个空间关系或动作，为什么能帮助理解这项内容”，而不是靠更多热点制造交互数量。

导航镜头与反馈如何跨层

事项空间或行为决定表达决定运行支撑
导航路径、地标和区域关系；移动、跳转、返回规则地图、当前位置、目的地与操作提示输入映射、位置状态、路径或传送实现
镜头可达视点、观察方向、移动和重置规则当前视角的构图、主次与过渡表现相机程序、遮挡与边界约束
反馈操作改变什么状态、何时成功或失败、怎样恢复高亮、文字、声音、状态动画状态同步、事件和错误处理

因此不能把全部导航归为 UI，也不能把全部镜头归为画面表现。系统划分是为了说清责任与联系，不是强迫每个元素只属于一个盒子。

设计依赖不等于单向流水线

设计时应先澄清目标，再共同推敲内容、空间与行为，用表达和实现的小样检验它们，并根据结果回改。技术试验可以提前，验证可以推翻布局；不能把目标、内容、空间、行为、表达、实现理解成只能从左到右完成一次。

这一组织方式借鉴了 Garrett 原著从策略到范围、结构、框架、表面的分层思路，以及层间相互依赖和双向反馈；本文的三维系统划分是项目自己的改编，不是原著原图，也不是 3D 网页官方标准。原著出版社试读章节

功能必需与实现选配

- 必需功能：目标清楚、内容可达、空间关系可理解、视角可控、操作有反馈、可以返回或恢复，以及可接受的加载、失败处理和替代访问路径。

- 依目标选配：自由行走、车辆、物理碰撞、地图、传送、配置器、任务、空间声音、昼夜系统等。每项应说明服务什么内容或任务。

- 装饰候选：删掉后不影响定位、理解、操作或任务完成的景物与效果。装饰不是禁用项，但应排在主体验之后，并承担性能成本。

装饰是作用，不是技术类别。雾可以帮助远近辨识，声音可以提供方向或操作反馈，动画可以解释状态变化。建筑、天空、地面不必全部存在；纯抽象空间同样可以成立。必需的是可理解的组织，不是现实世界物件清单。

十维检查清单

系统关系确定以后，用下面的十维检查是否遗漏具体功能。它是检查工具，不是十个互不相干的组成模块，也不能代替前面的关系设计。

维度必需功能依目标选配与取舍
1 目标与核心内容明确为谁设计、来做什么、最后应理解或完成什么作品浏览、机制学习、产品配置、创作、品牌体验；不要混成无优先级的功能集合
2 空间布局入口、目的地、区域关系、边界与尺度有可读线索房间、岛屿、街区、分层空间、传送门；空间路径应有内容理由
3 主体与环境主体清楚，环境提供必要参照，不压过内容建筑、植被、水、人物、车辆、抽象几何；无任务作用的摆件属于装饰候选
4 材质与光可见性、主次、深度线索与风格一致实时或烘焙光、阴影、PBR、反射、雾、后期；不必追求全部写实
5 镜头与移动初始视角合理、可控制且不易迷失，可回到有效观察位置俯视、第一或第三人称、轨道观察、导览；镜头应支持具体观察任务，不只是展示空间
6 交互与反馈可操作对象可辨识，动作有结果，可恢复、撤销或返回拾取、拖放、拆解、搭建、配置、物理、任务；先设计操作带来的理解，再选择技术
7 导航与界面操作提示、目标入口、方向线索、返回与恢复始终可用地图、指南针、搜索、快捷传送、进度；地图不是每站必需，辨方向才是必需
8 内容与叙事信息层级明确，关键内容不只藏在难发现的角落热点说明、章节、任务线、讲解角色、时间线；允许跳过开场，避免强迫等待
9 动画声音与模拟必要状态变化可理解；使用声音时可关闭，静音不丢关键内容转场、环境动画、旁白、空间音频、物理、天气；持续粒子和无目的摇镜应谨慎
10 加载性能适配与无障碍可理解的加载和失败状态，设备预算，键盘与触屏路径，可读文字与替代内容压缩、实例化、分区加载、LOD、自适应画质、2D 模式；减少运动、焦点管理和屏幕阅读器需真实验证

十维不是十个独立模块。目标决定空间布局，任务决定镜头与交互，内容决定导航；性能和可达性贯穿全过程。

三个原作者案例

Bruno Simon 让作品集成为驾驶空间

作者官网明确邀请访客驾驶探索，列出键鼠、触屏、手柄输入，以及地图、重生、静音、画质开关。作者仓库 README 描述输入、物理、玩家、视图、区域与交互点、渲染的更新顺序，并列出 GPU 友好纹理与 UI 图片的压缩流程。官网 · 作者仓库

设计推论：驾驶建立辨识度，也增加学习与迷路成本，因此导航、操作提示和脱困不是附属美化。车辆、物理、天气和昼夜是此项目的体验选择，不是所有 3D 网页的基础要求。

Choo Choo World 围绕搭建运行与分享组织空间

Lusion 将其定义为面向不同年龄用户的创作小游戏，并说明分享快照的参与机制。实站可读教程列有镜头平移、旋转与缩放、45° 快捷旋转、编辑与观看模式、撤销与重建、列车播放控制；界面文字还包含声音设置、导出图片及不支持设备、浏览器或 WebGL 的提示。作者项目说明 · 项目实站

设计推论：核心是“搭建—运行—观看—分享”，不是无目的漫游。错误恢复和模式切换直接服务创作，比增加景物重要。分享适合能产出用户成果的体验，不应机械移植。

Of The Oak 用视觉空间连接科普内容

Lusion 说明该网站是实体装置的网页延伸，为线上和现场观众提供深入理解项目的入口。其管线将复杂树、枝与节点结构压缩为约 3.5 MB 的自定义格式，并采用 WebGL instancing；这一数字不是整个网站的总下载体积。实站可读内容包括跳过开场、冥想体验和物种探索入口。作者项目说明 · 项目实站

设计推论：视觉复杂度不应直接等于重模型下载；资产管线与内容分支需要一并设计。跳过机制和清楚的内容入口，可以让空间体验不阻塞信息访问。

证据类型与使用限度

本次案例证据来自上述原作者网页正文、实站可读界面文案和作者仓库 README。正文能支持作者目标与技术说明，界面文案能支持所声明的入口与控制设计，README 能支持公开的系统组织和资产处理流程。

这些证据不等于实际 GPU 渲染与操作验收：本次未据此确认帧率、触屏手感、实时光材质表现、设备兼容性或真实降级效果。页面中存在错误提示文案，也不代表失败路径已经实测通过。设计推论已与来源事实分开。奖项、热度与技术新旧不作为可用性证明。

对 SD01 的应用

依据当时对 SD01 v0.2 的代码评审，该版本已以全视口场景作为主入口，但主要仍是可绕看的两件模型展台：用户能移动视角和打开说明，尚缺“看到什么—做什么—发生什么—理解什么”的操作学习链。这是设计与代码层面的判断，不是 GPU 体验测试结论。

后续 v0.3 已新增原型操作，但实际 GPU 运行与用户理解效果尚未验证；不能把 v0.2 的缺口描述直接当作 v0.3 的现状，也不能把新增操作当作学习有效的证明。

方法上应先明确一个学习任务，例如通过观察方向和受限操作理解转动连接或插接方向；让全景负责定位、局部视角负责看接点、返回空间负责比较。先完成一处可验证的小体验，再扩展另一处。新增建筑、小地图、热区和进度条可以改善导航，却不能单独解决内容与空间脱节的问题。

插接学习例子

以下是用于说明系统关系、仍需验证理解效果的设计例子，不是已完成 GPU 或用户验收的声明：

1. 目标：用户能解释插接为何受方向约束。

2. 内容：槽口形状、插入方向、允许与受限的移动。

3. 空间与行为共同设计：提供能看清槽口的观察位置；允许沿正确方向移动，错误方向受到约束，并可复位。对象朝向、间距和可达视角随任务调整。

4. 表达：以局部高亮、方向标记和简短文字解释约束；声音若采用，只作补充，不能独自承载对错信息。

5. 运行支撑：对象状态、移动约束、镜头与键盘等价操作保持一致；资源失败时仍可读到机制说明。

6. 验证与反馈：看用户能否说明为什么一个方向可插入、另一方向不可，而非只统计点击或到访次数。若不能，回查内容、空间和行为的关系，而不是先追加特效。

这条链把同一学习目标映射到各部分，因而比“模型、灯光、热点、地图都已经有了”的清单结论更能判断设计是否成立。

可复用评审问题

1. 不读长说明，用户能否知道来做什么、第一步做什么？

2. 每个区域为什么存在？它与其他区域的关系是否可辨？

3. 三维观察或操作带来了二维卡片难以表达的什么信息？

4. 是否能写出一条完整的“看到—操作—反馈—理解”链？

5. 可操作对象与装饰是否容易区分？错误操作能否恢复？

6. 镜头是否揭示内容，而不只是把模型框进画面？

7. 迷路、卡住、关闭弹层后，能否继续或回到起点？

8. 关键内容能否不用精细鼠标操作、强制运动或声音来获取？

9. 在低性能设备、资源失败和无 3D 支持时，用户还剩什么可用功能？

10. 删除某项效果会损失哪项功能？若没有，它的视觉收益是否值得性能成本？

11. 结论分别由文案、代码、静态图、实时 GPU、真机或用户测试中的哪一级证据支持？

最小完整版本可以只有一个主题空间、少量明确目的地、一种可靠移动方式、内容交互、方向与恢复机制，加上加载失败处理和替代内容。先证明探索与理解闭环，再增加模拟和装饰。
